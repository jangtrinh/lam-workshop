Core Concept: The Token Extraction Pipeline

NGHE — KHÁI NIỆM CHÍNH
TRANSCRIPT

Pipeline rất đơn giản. Input: 4 screenshots của key screens. Process: Gemini multimodal extraction với prompt cụ thể — "Extract all visual constants: colors, fonts, spacing, border radius, shadows." Output: Token table có cấu trúc, dev-ready, version-controlled. Bí quyết: chỉ cần 4 screens, không phải 40. Hero, detail, form, dashboard — 4 loại này cover 90% token usage.

INPUT                    PROCESS                     OUTPUT
4 screenshots    ->    Gemini multimodal      ->    Token Table
(key screens)          "Extract all visual           (structured,
                        constants: colors,            dev-ready,
                        fonts, spacing,               version-controlled)
                        radius, shadows"

Extraction Prompt

Analyze these 4 screenshots and extract ALL design tokens.
Output as a Markdown table with columns: Token Name | Value | Usage

Rules:
- Use semantic names (NOT color-1, USE surface-primary)
- Colors: exact hex values from the screenshots
- Typography: font-family, size (px), weight, line-height
- Spacing: exact px values used for margin/padding patterns
- Border radius: all unique radius values found
- Shadows: complete box-shadow CSS values

Categories to cover:
1. Color tokens (surface, text, border, accent, state colors)
2. Typography tokens (display, heading, body, caption, label)
3. Spacing tokens (4px grid — xs/sm/md/lg/xl/2xl)
4. Effect tokens (shadow-sm, shadow-md, radius-sm, radius-md, radius-lg)

After the table, flag any value you extracted that you are less than 90% confident about.

ATTENTION HOOK — THE 4x3 PROBLEM

Mỗi button có 4 states (default, hover, active, disabled) × 3 variants (primary, secondary, ghost) = 12 combinations. Card component: 3 states × 4 variants × 2 sizes = 24 combinations. Document manual mất hàng giờ mỗi component.

Core Concept: The Component Spec Template

NGHE — KHÁI NIỆM CHÍNH
TRANSCRIPT

Template component spec có 8 phần. Anatomy là các parts cấu thành component. Variants là các biến thể: primary, secondary, ghost. States là các trạng thái: default, hover, active, disabled, loading, error. Tokens Used là map các token từ session 2.1 vào component. Responsive là cách nó scale hoặc reflow. Accessibility là ARIA roles, focus, contrast. Do's là cách dùng đúng với ví dụ. Don'ts là cách dùng sai với ví dụ. Feed template này cùng token set vào AI Studio.

COMPONENT: [Name]
├── ANATOMY       (các parts cấu thành: label, icon, container, state overlay)
├── VARIANTS      (primary, secondary, ghost, destructive...)
├── STATES        (default, hover, active, disabled, loading, error)
├── TOKENS USED   (map tokens từ Session 2.1 vào component)
├── RESPONSIVE    (cách scale/reflow ở breakpoints)
├── A11Y          (ARIA roles, keyboard focus, color contrast ratios)
├── DO's          (cách dùng đúng với ví dụ cụ thể)
└── DON'Ts        (common misuse với ví dụ cụ thể)

AI Studio System Instruction

Setup AI Studio với system instruction này một lần — sau đó chỉ cần paste token set và component name:

You are a design system documentarian with 10 years of experience.

Given a component name and a token set, produce a COMPLETE component spec.

## Output format (strict — follow exactly):

### COMPONENT: [Name]

**ANATOMY**
[List all sub-parts with descriptions]

**VARIANTS**
[Table: Variant | When to use | Token differences from default]

**STATES**
[Table: State | Visual change | Token used | Accessibility note]

**TOKENS USED**
[Table: Property | Token Name | Value | Applies to]

**RESPONSIVE**
[Describe behavior at 320px / 768px / 1280px]

**A11Y**
- ARIA role: [role]
- Keyboard: [Tab, Enter, Space behavior]
- Contrast: [ratio requirement, which tokens ensure it]
- Screen reader: [what gets announced]

**DO's** (minimum 3)
[Each with a concrete scenario]

**DON'Ts** (minimum 3)
[Each with what goes wrong if violated]

## Rules:
- Every value must reference a token name, NEVER hardcode
- If token set doesn't cover a needed value, FLAG it (do not invent)
- States must be exhaustive — never skip disabled or error

Core Concept: The Audit Loop

NGHE — KHÁI NIỆM CHÍNH
TRANSCRIPT

Audit loop gồm 4 bước. Screenshots của 4+ screens được load vào Gemini. Gemini multimodal analysis compare screens với token set và flag bất kỳ giá trị nào deviate. Deviation report được generate với specific values: expected vs actual, cụ thể đến từng screen và element. Sau đó fix, re-screenshot, re-audit. Vòng lặp tiếp tục cho đến khi 0 deviations. Đây là verification loop đóng Gap 3.

Audit Prompt

I am providing [N] screenshots and my design token set below.

## Task
Compare each screenshot against the token set. For every visual element:
1. Identify what token it should be using
2. Estimate the actual value from the screenshot
3. Flag if the estimated value deviates from the token value

## Output format (strict):
### Deviation Report

| Screen | Element | Expected Token | Expected Value | Estimated Actual | Deviation |
|--------|---------|----------------|----------------|------------------|-----------|

If 0 deviations found, explain your analysis reasoning — do not just say "all good."

## Token Set
[Paste full token table from Session 2.1]

## Severity classification:
- CRITICAL: visible mismatch (color family wrong, size off by 4px+)
- MODERATE: subtle mismatch (hex off by 1-2 digits, spacing off by 2px)
- INFO: potential issue worth checking manually
KEY INSIGHT

Đây là feedback loop mà Lam's Grand Masterplan đang thiếu (Gap 1, Gap 3). Output không được accept — nó được audit, corrected, và re-audited. Deviation report được lưu trong git cùng token set — tạo audit trail, đóng Gap 5 (version control).

LEVEL 2 SELF-CHECK QUIZ
Q1: Tại sao extract tokens từ screenshots thay vì Figma files?
  • A) Nhanh hơn
  • B) Screenshots cho thấy những gì thực sự ship — grounded trong reality
  • C) Figma không export được tokens
  • D) Figma hay bị lỗi
B — Figma tokens là aspirational (những gì designer muốn). Screenshot tokens là actual (những gì thực sự render). Gap giữa hai thứ này là nguồn gốc của Gap 4 trong Grand Masterplan. Chỉ có production screenshots mới cho tokens grounded trong reality.
Q2: AI cần tối thiểu thông tin gì để generate component spec hữu ích?
  • A) Tên component mà thôi
  • B) Tên component + token set
  • C) Tên component + token set + screenshot ví dụ
  • D) Tên component + Figma link
B — Tên component + token set là minimum. Không có token set, AI sẽ invent values và những invented values đó sẽ drift khỏi design thực tế. C (thêm screenshot) tốt hơn nhưng B là minimum viable.
Q3: Consistency audit tìm ra 0 deviations trong lần chạy đầu tiên. Bạn kết luận gì?
  • A) Design hoàn hảo — ship ngay
  • B) Kiểm tra xem token set có quá loose hoặc audit prompt có quá lenient không
  • C) Skip audit lần sau
  • D) Tăng số screens cần audit
B — 0 deviations on first try thường là signal của vấn đề với chính audit, không phải design. Token set có thể quá broad (e.g., "color-primary: any shade of blue") hoặc audit prompt không specific. Luôn question 0-deviation results.
Q4: Button spec hiển thị "border-radius: 8px" nhưng token set nói "radius-md: 6px." Chuyện gì đã xảy ra?
  • A) AI làm tròn số lên
  • B) AI invented một token thay vì dùng token set của bạn — token set chưa được load
  • C) Cả hai đều đúng, có thể dùng cả hai
  • D) 6px và 8px không có sự khác biệt đáng kể
B — Đây là dấu hiệu điển hình của token set chưa được load đúng cách. AI default về values "phổ biến" thay vì values của bạn. Fix: luôn paste toàn bộ token table vào prompt trước khi yêu cầu component spec.
Q5: Điều gì làm cho audit loop là "feedback loop" thay vì chỉ là one-time check?
  • A) Nó chạy tự động
  • B) Fix → Re-screenshot → Re-audit cho đến khi 0 deviations
  • C) Nó generate report
  • D) Nó dùng nhiều screens hơn
B — Feedback loop nghĩa là output của vòng trước trở thành input của vòng tiếp theo. Fix → Re-screenshot → Re-audit là vòng lặp — không phải điểm dừng. Đây là thứ đóng Gap 1 (no feedback loops) và Gap 3 (no verification) trong Grand Masterplan.
